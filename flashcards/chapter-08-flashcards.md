## Chapter 8: Chunking, RAG Patterns, and Unstructured Data Prep — Flashcards

| # | Front (Question) | Back (Answer) |
|---|-----------------|---------------|
| 1 | What are the five stages of a standard end-to-end RAG pipeline? | Ingest → Chunk → Embed → Retrieve → Generate. Exam tip: retrieval quality should be evaluated BEFORE wiring in the generation step. |
| 2 | Typical chunk size range used as a starting point for text embedding (in tokens)? | Roughly 200–500 tokens is a common starting range for general text; exact optimal size depends on document structure and embedding model context limit. Exam tip: too small loses context, too large dilutes relevance. |
| 3 | Typical chunk overlap percentage used to preserve cross-boundary context? | Roughly 10–20% of chunk size is a common convention. Exam tip: 0% overlap risks splitting facts across chunk boundaries; overlap increases embedding cost slightly by re-embedding shared text. |
| 4 | Fixed-size chunking vs recursive/structure-aware chunking — when to use each? | Fixed-size: simple, fast, works for uniform plain text. Recursive/structure-aware: splits on natural boundaries (headings, paragraphs, sections) — use for documents with hierarchical or procedural structure. Exam tip: structure-aware chunking reduces broken-context retrieval. |
| 5 | Semantic chunking vs fixed-size chunking? | Semantic chunking groups text by meaning/topic shift (often using embedding similarity), producing variable-length coherent chunks. Fixed-size chunking splits by a set character/token count regardless of meaning. Exam tip: semantic chunking costs more compute but improves retrieval on complex documents. |
| 6 | Why tag chunks with metadata (e.g., region, date, department) at ingestion time? | Enables filtered retrieval — the retriever can restrict search to a subset of chunks matching metadata before or during vector search. Exam tip: metadata filtering happens at retrieval time, not generation time. |
| 7 | How should retrieval quality be evaluated before adding a generation model? | Use a labeled test set of queries with known relevant chunks; measure metrics like precision, recall, or hit rate at top-k. Exam tip: never rely on the LLM's fluent output to judge whether retrieval worked — it can mask irrelevant context. |
| 8 | Structured data prep for Gen AI: what does it typically involve? | Cleaning (nulls, duplicates), schema normalization, and feature framing for direct querying or as tool/function-call input. Exam tip: structured data is usually NOT chunked and embedded the same way as free text. |
| 9 | Unstructured data prep for Gen AI: what does it typically involve? | Text extraction, cleaning, chunking, embedding, and metadata tagging to support RAG retrieval. Exam tip: PDFs/semi-structured files need layout-aware extraction before chunking. |
| 10 | What problem occurs if a PDF parser ignores multi-column layout during extraction? | Text from different columns gets interleaved out of reading order, corrupting chunk content and degrading retrieval relevance. Exam tip: use a layout-aware parser for mixed-layout PDFs, not naive text extraction. |
| 11 | What happens if chunk size is set larger than the embedding model's max token limit with no truncation handling? | The request may fail or the input gets silently truncated, losing the end of the chunk's content. Exam tip: always leave margin below the hard token limit to account for tokenizer overhead. |
| 12 | Generic pseudocode pattern for chunking with overlap (conceptual, framework-agnostic) | `chunks = split(text, chunk_size=400, chunk_overlap=50)` — each chunk shares ~50 tokens with the previous one. Exam tip: this overlap parameter is the standard lever for balancing context continuity vs embedding cost. |
