## Chapter 4: Cortex Search: Building Retrieval and RAG Pipelines — Flashcards

| # | Front (Question) | Back (Answer) |
|---|-----------------|---------------|
| 1 | What retrieval technique does Cortex Search use by default? | Hybrid search — combines vector (semantic) similarity and keyword/lexical matching in a single ranked result. Exam tip: this is the main differentiator vs. a manual VECTOR_COSINE_SIMILARITY query. |
| 2 | What clause in CREATE CORTEX SEARCH SERVICE defines which columns can be used to filter search results? | ATTRIBUTES. These columns are NOT embedded for semantic search — only the column in the ON clause is searched/embedded. Exam tip: ATTRIBUTES = filter metadata, ON = searchable text. |
| 3 | What parameter controls how frequently a Cortex Search service refreshes to reflect base table changes? | TARGET_LAG (e.g., '1 hour', '1 day') — same concept as Dynamic Tables. Lower TARGET_LAG = fresher data but more compute usage. |
| 4 | Cortex Search vs. manual VECTOR column + VECTOR_COSINE_SIMILARITY — key difference? | Cortex Search is fully managed: auto-generates embeddings, auto-refreshes index, and blends semantic + lexical relevance. Manual VECTOR approach requires you to generate embeddings and manage similarity queries yourself. |
| 5 | Which function is used to query a Cortex Search service directly in SQL for testing/preview? | SNOWFLAKE.CORTEX.SEARCH_PREVIEW('service_name', '<json request>') — request includes query text, columns, filter, and limit. |
| 6 | In a RAG pipeline, what is the correct order of operations using Cortex Search + COMPLETE? | 1) Query Cortex Search to retrieve relevant context/passages 2) Build a prompt combining that context + the user question 3) Pass the prompt to COMPLETE. Exam tip: retrieval always happens BEFORE generation. |
| 7 | How do you restrict Cortex Search results to only rows matching an attribute value (e.g., department = 'Finance')? | Include a 'filter' object in the JSON request passed to SEARCH_PREVIEW / the search API, referencing an ATTRIBUTES column. Filtering is push-down, not post-query. |
| 8 | What compute resource is required by a Cortex Search service and drives both refresh and query performance? | A virtual WAREHOUSE, specified via the WAREHOUSE parameter at service creation. Scaling this warehouse improves throughput/latency under load. |
| 9 | Which column type does Cortex Search embed/index for semantic search? | Only the column specified in the ON clause of CREATE CORTEX SEARCH SERVICE — this is the searchable text column, distinct from ATTRIBUTES filter columns. |
| 10 | Exam trap: What's wrong with concatenating Cortex Search output and COMPLETE output independently without passing context between them? | This breaks the RAG pattern — COMPLETE never sees the retrieved context, so the answer is not grounded in retrieved documents. Context must be inserted into the COMPLETE prompt. |
| 11 | Why might lowering TARGET_LAG NOT fix slow query latency? | TARGET_LAG controls freshness/refresh cadence, not query-time performance. Query latency under load is addressed by warehouse sizing/scaling, not TARGET_LAG. |
| 12 | When should you choose Cortex Search over calling COMPLETE directly on raw table data? | When you need relevant context retrieved from a large corpus before generation (RAG). COMPLETE alone has no retrieval/ranking mechanism and can't ground answers across many rows. |
